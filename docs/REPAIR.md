# LatticeVale 14.6.0 Resume / Repair

## Use Option 1 for an existing installation

Launch the **full 14.6.0 release** and select **Resume / repair installation**. The repair engine proves managed ownership, reads historical installer metadata, creates the required rollback backup before managed-source refresh, stages the current management layer, migrates schemas, regenerates derived architecture state, and resumes from the earliest stale/incomplete dependency.

## Repair dependency order

14.6.0 makes the principal dependency chain explicit:

1. durable `install-options.json` schema/migration;
2. Windows hardware snapshot;
3. live WSL hardware capabilities;
4. backend capabilities/health and adapter selection;
5. canonical runtime resource policy;
6. generated Compose/service configuration;
7. service/runtime verification;
8. Windows integrations.

A changed upstream layer invalidates only its dependent derived layers. Persistent application data and user-owned overrides are not treated as disposable derived state.

## Generated-state rule

A current LatticeVale component must accept the state generated by another current component. 14.6.0 therefore validates current options through the canonical schema implementation and validates resource-policy generation with the same canonical memory-budget API used by verification and state audit. Runtime backend health is tracked separately from policy topology: a safe DirectML-to-Ollama fallback does not make the just-generated policy stale unless a resource-relevant topology/acceleration fact actually changed.

Future schemas fail closed. Known historical schemas are migrated by the installer rather than accepted blindly.

## Safe repeated repair

Option 1 is designed to converge. Re-running it after a successful repair should normally verify healthy state or perform only newly stale work; it must not recreate persistent identities or databases merely because a derived hardware/policy fingerprint changed.
