LATTICEVALE v14.6.0 — INSTRUCTIONS
V14.6.0 CANONICAL ARCHITECTURE: durable installer choices are separated from derived Windows/WSL hardware, backend capability/health/selection, and runtime policy. DirectML, CUDA, ROCm, Vulkan, native-Windows Ollama, and CPU are classified independently; generated architecture state is schema-versioned, fingerprinted, atomically written, and canonically validated. Resume / repair migrates recognized managed 14.x installations preservation-first.
V14.5.47 WSL GPU RECOVERY: DirectML now applies the selected Windows adapter before torch-directml initialization, retains exact runtime adapter proof, and can use installer-recorded DXDiag dedicated VRAM only when the runtime cannot report usable capacity. Hard fallback is runtime-fingerprinted so changed WSL/GPU state retries once. Managed Ollama adds verified Vulkan mode for existing /dev/dri/renderD* devices. The new GPU audit/diagnose paths are read-only; NVIDIA CUDA, AMD/ROCm, CPU, DirectML, and native-Windows Ollama remain supported; Windows/vendor display drivers stay external.
V14.5.46 GPU-AWARE ONBOARDING: LatticeVale now detects recognized Windows GPU vendors and probes the selected WSL distro before the local-AI questions. It marks the recommended backend/acceleration option, reuses compatible installer-owned WSL prerequisites, and installs missing selected-path DirectML/NVIDIA prerequisites when safe. AMD ROCm remains gated by real /dev/kfd + /dev/dri; Windows/vendor display drivers are never silently installed or replaced.
V14.5.45 POWERSHELL COMPATIBILITY HOTFIX: LatticeVale no longer creates .NET generic collections with New-Object. Installer, uninstall, repair/reset, and relay PowerShell paths use direct ::new() constructors, and list-returning helpers use explicit ToArray() where appropriate. This prevents the PowerShell 7.6 "Argument types do not match" binder crash after otherwise-successful DirectML detection; users do not need to edit scripts or downgrade PowerShell.

V14.5.44 DIRECTML PREFLIGHT HOTFIX: DirectML selection now uses a dedicated direct /dev/dxg probe with normal-user-to-root retry, separately checks WSL-projected libd3d12/libd3d12core/libdxcore, distinguishes probe failure from confirmed bridge absence, and can run a real tensor probe when an existing installer-owned DirectML venv is present. The broader Ollama GPU prerequisite parser is no longer used to decide DirectML /dev/dxg availability.

RESOURCE POLICY DIAGNOSTIC: after a successful v14.6.0 install/repair with adaptive limits enabled, `~/hermes-stack/resource-policy-report.txt` is the secret-free human-readable explanation of canonical policy v12. It records RAM/CPU class, managed-Ollama acceleration/offload verification, GPU topology/VRAM coordination, context/model floor, generated CPU/RAM limits, and hardware/policy fingerprints. `./manage.sh audit` independently recomputes the fingerprints and verifies live Docker ceilings.

EXISTING INSTALLS / UNIVERSAL REPAIR MIGRATION: run the full v14.6.0 installer directly and choose Resume / repair installation. For any older recognized installer-managed stack, v14.6.0 inherits and extends the v14.5.43 migration engine: it proves ownership, detects historical version/schema state, creates a verified rollback backup, installs the current installer-owned management layer, replays required cumulative migrations, refreshes current managed pins, and regenerates canonical hardware/backend state plus resource policy v12. No intermediate LatticeVale version is required. Unrecognized/corrupt stacks and repair downgrades fail closed. Same-version repair remains local-first.

V14.5.42 HARDWARE RESOURCE POLICY UPDATE: Managed WSL/Docker Ollama now uses resource policy v11 with compact/balanced/large RAM profiles, CPU profiles, per-GPU NVIDIA/AMD VRAM topology, GPU-aware context, shared DirectML/Ollama VRAM coordination, and runtime GPU-offload verification. Auto-selected GPU acceleration that actually runs on CPU is re-budgeted safely; explicitly forced GPU acceleration fails closed when offload cannot be proven. Native Windows Ollama remains user-owned.

V14.5.4 DIRECTML / LOW-MEMORY UPDATE: Local AI setup can explicitly choose stable Ollama or the experimental PyTorch DirectML text gateway. DirectML is opt-in; existing installs stay on Ollama unless changed. When selected, Hermes and Honcho text use the shared WSL-host gateway, Ollama remains fallback, and Honcho embeddings stay on Ollama. SEARXNG OPERATIONAL NOTE: SearXNG is local, but the search engines it queries are external. `web_search` can execute successfully and still temporarily return no results when upstream engines rate-limit, CAPTCHA, or suspend automated requests. ================================================================================
1. BEFORE YOU START
================================================================================

1. Use Windows 10/11 x64/AMD64 build 19041 or newer with Administrator access. Windows PowerShell 5.1 and PowerShell 7.x are supported by the shipped entry points.
2. Install and verify Microsoft WSL separately before using LatticeVale.
3. Have an existing Ubuntu 22.04, 24.04, or 26.04 WSL2 distro using amd64/x86_64.
4. Confirm the distro launches normally and has a normal non-root sudo user with a home under /home/.
5. Fresh installs require the Windows volume backing the selected WSL distro to be over 50 GiB total capacity and have at least 50 GiB free. An existing installer-managed stack may Resume / repair with at least 10 GiB free; LatticeVale confirms managed ownership before applying that lower repair floor.
6. Have Internet access for packages, container images, provider authentication, and any models that must be downloaded.
7. If you intend to use native Windows Ollama, install it separately first. LatticeVale can use and launch an existing native Ollama, but does not install or update that Windows application.
8. Extract the complete release ZIP to a normal Windows folder. The official package contains one top-level `Lattice-Vale` folder. Do not run `installer\Install-LatticeVale.ps1` from inside a ZIP viewer.

LatticeVale does NOT create, import, move, unregister, convert, or repair WSL distributions during normal installation. Normal configuration/runtime paths do not create or switch global WSL `networkingMode`; an existing externally configured mirrored mode is used only if it already works. The sole v14.4.81+ exception is the explicitly approved mirrored→NAT compatibility fallback after persistent `E_UNEXPECTED` during bounded preflight recovery.

If WSL itself fails during preflight with `Catastrophic failure` / `Wsl/Service/E_UNEXPECTED`, do not unregister the distro or delete its VHDX. v14.4.82 retains the bounded recovery during the same installer run when the failed distro is required or explicitly selected. It first performs `wsl --shutdown`, waits briefly, and retests the same registered distro without changing `.wslconfig` or Windows features. If other WSL distros are running, the installer asks before the global shutdown.

If the same failure persists and `%UserProfile%\.wslconfig` explicitly selects mirrored networking, the installer can offer a separate explicit NAT compatibility recovery. Accepting it backs up `.wslconfig`, changes only `[wsl2] networkingMode` to `nat`, preserves unrelated settings, restarts WSL, and retests the same distro. If bounded recovery is not enough, the installer prints the elevated command for `tools\Repair-LatticeVale-WslHost.ps1`; deeper DISM/feature repair remains an explicit administrator action and is not run automatically by normal install/repair.

================================================================================
2. VERIFY THE RELEASE
================================================================================

From the extracted LatticeVale folder, optionally verify the complete shipped release tree:

  powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\installer\verify-release.ps1

The installer performs the same source-manifest verification by default before executing the core installer. This verifies the extracted LatticeVale release files and exact SHA-256 manifest coverage; it does NOT verify the health of an already-installed Hermes stack. Live-stack verification is covered in section 6.

The ExecutionPolicy Bypass argument applies only to that launched PowerShell process. It does not change your stored Windows execution policy and is not a substitute for reviewing trusted source.

================================================================================
3. START THE INSTALLER
================================================================================

Open PowerShell AS ADMINISTRATOR in the extracted LatticeVale folder and run:

  powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\installer\Install-LatticeVale.ps1

Optional explicit distro selection:

  powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\installer\Install-LatticeVale.ps1 -DistroName <your-distro-name>

Do not assume a distro is named Ubuntu-24.04. Use the name shown by:

  wsl --list --verbose

The installer will detect eligible distros, verify WSL2/Ubuntu/architecture/storage, and ask you to choose an existing Ubuntu user.

================================================================================
4. CLEAN INSTALL — STEP BY STEP
================================================================================

1. Select an eligible existing Ubuntu WSL2 distro.
2. Select the existing non-root Ubuntu user that should own the LatticeVale stack.
3. Answer the explicit component questionnaire. Suggested values are guidance only; where the installer says an explicit choice is required, pressing Enter alone does not select the suggestion.
4. Select only features you intend to use. Read the explanation shown with each system/network-affecting choice.
5. Configure the default Hermes provider/model when Hermes prompts for it.
6. If adding named profiles, choose each profile name/role and whether it should clone the default provider/model or configure its own.
7. If enabling Kanban, choose concurrency values appropriate to the machine and intended automation level.
8. If enabling Matrix, select whether named profiles should receive dedicated Matrix identities/rooms.
9. If enabling Windows Tailscale exposure, choose the requested private HTTPS ports and review the networking prompt carefully. Current fresh suggestions are 9443 for Dashboard and 443 for Matrix; existing managed values are preserved when possible.
10. If enabling **Obsidian integration**, enter a Windows-local drive path for the vault, not a \\wsl.localhost or SMB path. QMD can be used without Obsidian and does not by itself require a Windows vault path.
11. If enabling local AI, choose managed WSL/Docker Ollama or an already-installed native Windows Ollama when offered, then choose models/acceleration as prompted.
12. Review the complete configuration summary.
13. Confirm installation.

V14.4.5 REPAIR RACE HARDENING
During Resume / repair, LatticeVale may reconcile ownership on live installer-owned Hermes/QMD/log trees. SQLite WAL/SHM files and rotated logs can disappear normally while services are active. v14.4.5 tolerates only those exact vanished entries; an ownership or permission failure for a path that still exists remains fatal. Do not manually delete the Hermes data tree to work around this class of error.

14. Let the staged installer finish. If interrupted, rerun the same installer and choose Resume / repair instead of deleting state.

================================================================================
5. EXISTING INSTALL — CHOOSE THE CORRECT MODE
================================================================================

Before launching the Windows installer for a repair or controlled update/repair run, use **Shut Down LatticeVale** first when available. v14.4.84 stops the managed stack but intentionally leaves the WSL distro running. Do not use targeted `wsl --terminate`; if an older LatticeVale-owned shutdown helper is detected, Resume / repair performs the required bounded `wsl --shutdown` + `WslService` transport reset itself.

When a managed stack is detected the installer offers:

1. Resume / repair installation
   Use for an interrupted, incomplete, stale, or partially unhealthy installation. Reuses saved choices and repairs/verifies the existing stack. It explicitly repairs stale adaptive runtime/RAM policy and performs the bounded installer-owned component refresh when the periodic age gate is due, the managed-refresh policy revision changes, or legacy refresh state is missing. A bundle-version change alone remains local-first; choose Option 6 to force package/image/source refresh immediately.

2. Change installed components
   Use when you want to enable/disable or change selected LatticeVale features. Unselected configuration scopes are retained from the saved installation. Component removal is designed to preserve associated persistent data unless an explicitly destructive recovery path says otherwise. If a selected change makes a dependent integration impossible (for example disabling Dashboard while its LatticeVale-owned Tailscale exposure is still selected), only that dependent integration is disabled and the installer explains the normalization. Turning the installer-owned default Ollama provider off forces the default Hermes provider/model wizard in the same run so stale Ollama provider configuration is not silently retained.

   Current change scopes are:
     1) Optional components: Dashboard, SearXNG, QMD, Obsidian
     2) Kanban enablement/concurrency
     3) Matrix + Windows Tailscale
     4) Local AI / Honcho / Ollama backend/models
     5) Runtime/Windows policy: container limits, updates, WSL lifetime, auto-start, shortcuts, timezone
     6) Select all categories
     7) Finish

3. Verify installation only
   Read-only verification path for the persistent installation. Use when you want diagnostics without changing stack configuration.

4. Reconfigure providers/profiles
   Use to rerun Hermes provider/model/profile setup while retaining the rest of the service/data selections. This operates within the saved component policy: if the default profile is intentionally configured for LatticeVale local Ollama, this option reapplies that local-AI policy. Use Option 2 -> Local AI / Honcho / Ollama to switch the default profile between installer-owned Ollama and an external provider.

5. Advanced recovery
   Use only for the specifically described recovery action. Read the confirmation text. Identity-changing Matrix recovery requires the shared Matrix service to be enabled and is transactional: it preserves/reuses the existing human Matrix admin identity and all secondary-profile identities/rooms, backs up the current default bot credentials and default Matrix crypto store first, persists replacement default-bot bootstrap/device state, and only then retires the old installer-owned default runtime identity. Normal Resume / repair does not rotate that identity or delete its crypto store.

   Current recovery actions are:
     1) Reset checkpoints and reverify/reconcile every stage
     2) Rebuild only installer-owned Matrix bot/room identity
     3) Rerun provider/profile setup and reset checkpoints
     4) Return to read-only verification and exit

6. Update / repair installer-managed software
   Use a newer LatticeVale bundle to immediately apply that bundle's tested/declared installer-managed package/image/source versions. A verified bundle-owned pre-update safety backup must succeed before the forced refresh starts; it does not depend on the currently installed manage.sh and runs only that backup transaction as WSL root so container-owned persistent files can be preserved safely.

If you are unsure and simply need to recover a managed installation, choose option 1.

Practical image/container rule:
- Option 1 may recreate/reconcile affected containers when configuration, resource policy, migrations, or health require it. It may also refresh installer-owned images/packages/source when the 30-day gate, managed-refresh revision, or missing legacy refresh state requires that refresh. It does not force a pull/rebuild merely because the LatticeVale bundle version changed.
- Option 6 is the explicit choice when your goal is to force the current bundle-aligned installer-managed package/image/source refresh now. Persistent application data and explicit user-owned overrides remain preservation-first.

6. AFTER INSTALLATION — VERIFY HEALTH
================================================================================

From Windows PowerShell, the simplest full live-stack verification is:

  wsl -d <DISTRO> -u <LINUX_USER> -- bash -lc 'cd "$HOME/hermes-stack" && ./manage.sh verify'

A successful current installation reports:

  LatticeVale verification: HEALTHY

For additional detail, open the selected Ubuntu WSL distro as the same Linux user chosen during LatticeVale installation, then run:

  cd ~/hermes-stack
  ./manage.sh verify
  ./manage.sh audit
  ./manage.sh status
  ./manage.sh profiles
  ./manage.sh matrix-info

`verify` checks the live selected stack and integrations; `audit` gives the more detailed state classification used by repair diagnostics. These are distinct from `installer\verify-release.ps1`, which verifies the extracted release files rather than the installed runtime.

If the installer reports a pending secondary Matrix profile, also read:

  cat MATRIX-SECONDARY-PROFILES.txt

Then complete only the profile named in that file:

  ./manage.sh matrix-profile-finish <profile>

Do not manually copy Matrix tokens or invent room IDs when the installer has preserved a retryable pending state.

================================================================================
8A. RAM / ADAPTIVE RESOURCE POLICY
================================================================================

If you selected adaptive CPU/RAM ceilings, current v14.6.0 uses canonical resource policy v12. The audit measures CPUs actually available to the WSL process using the same effective semantics as `nproc`, while RAM fingerprint comparison uses the current WSL-visible allocation. These are per-stack ceilings/tuning defaults; they do not write or replace host-wide WSL memory policy.

Policy v12 has no fixed host-RAM band table and no machine/model-specific tuning branch. The canonical architecture library derives host reserve, DirectML WSL-host reserve, total container budget, CPU quotas, service-memory water filling, model/context/concurrency limits, GPU coordination, and allocator/PostgreSQL/Synapse tuning from live WSL CPU/RAM plus enabled services, actual model information, selected backend, and measured GPU/UMA capability. Generation, verification, diagnostics, repair planning, and state audit consume the same canonical calculations.

DirectML is a WSL-host workload and remains valid independently of Linux-native CUDA/ROCm/DRM enumeration. DirectML model admission uses the selected Windows adapter's canonical memory evidence when the runtime cannot report capacity. High-confidence dedicated/full-capacity measurements outrank legacy 32-bit lower-bound telemetry. UMA/shared-memory adapters receive a conservative ceiling bounded by Windows shared-memory evidence and live WSL RAM. If no trustworthy bounded capacity exists, DirectML fails model admission and retains the configured Ollama fallback.

Runtime health and resource topology have separate fingerprints. A transient DirectML execution failure can activate Ollama fallback without making policy v12 stale, because the configured DirectML host reserve remains part of the safe topology for retry. CUDA/ROCm/Vulkan Auto fallback to CPU may trigger policy regeneration when it changes the managed-container resource envelope. Explicit backend/GPU intent is preserved rather than silently rewritten.

Policy v12 verifies that generated service ceilings fit the managed budget and refuses impossible combinations instead of shrinking critical services below safety floors. Final reconciliation compares effective merged Compose memory/CPU ceilings with Docker `HostConfig.Memory` and `HostConfig.NanoCpus`, so repair cannot succeed with stale live cgroup limits. `compose.override.yaml` remains user-owned, is applied last, and may intentionally override generated ceilings.

LatticeVale does not write global WSL `memory` or `autoMemoryReclaim`. If you manage those values in `%USERPROFILE%\.wslconfig`, they remain your host-wide settings and affect more than this stack.

9. KANBAN AND AGENT-MANAGED SKILLS
================================================================================

Kanban is shared across profiles using the same Hermes data root. Dispatcher workers receive a real task binding; normal chat sessions do not.

Operational rules:
- create root work through normal Kanban creation/triage rather than pretending an ordinary chat is a claimed worker;
- do not manually pass the literal text $HERMES_KANBAN_TASK as a task ID;
- task-scoped complete/block/review/heartbeat operations require an actual bound or explicit task ID;
- completed task results should be read from retained task results/attachments rather than assuming scratch worker directories still exist;
- if asking Hermes for "the results," specify whether you want the substantive task output or board/status information when ambiguity matters.

For agent-managed skills:
- valid skill names are slugs, not arbitrary display names with spaces;
- malformed SKILL.md/frontmatter must be corrected rather than retried unchanged;
- existing skills should be viewed before patching when Hermes requires the current contents;
- tool-loop hard stops should remain enabled.

Fresh installer-managed profiles default `skills.write_approval` to `false` when no explicit setting exists, allowing automatic skill writes. If you want a separate human approval gate, set it to `true`. LatticeVale preserves an existing explicit approval choice during repair/update.

================================================================================
14. TROUBLESHOOTING / RECOVERY
================================================================================

If installation or repair is interrupted:
1. do not delete the WSL distro, Docker volumes, Matrix crypto state, profiles, or databases;
2. use **Shut Down LatticeVale** to stop the managed stack before rerunning the Windows repair installer; do not target-terminate the distro; v14.4.84 will repair legacy shortcut transport state when detected;
3. rerun `installer\Install-LatticeVale.ps1`;
4. choose Resume / repair;
5. follow the first concrete error reported;
6. use Advanced recovery only when its described action matches the failure.

Remember the execution layers are different:
- Windows host
- Ubuntu WSL host
- hermes-agent container
- other Compose containers

A command that exists inside the Hermes image may not exist directly on the WSL host. When using bash -lc inside the Hermes container, call /opt/hermes/.venv/bin/hermes explicitly if the login shell does not place it on PATH.

If the exact preflight failure is `Wsl/Service/E_UNEXPECTED` / `Catastrophic failure`, allow the v14.4.82 bounded recovery path to run first when it is offered. It retries the same registered distro after a controlled WSL restart and then re-runs normal eligibility checks. If that bounded path fails, or WSL is broken in another way, use the explicit host-repair guidance/tool printed by LatticeVale or repair WSL separately; do not unregister the distro or delete its VHDX as a first response.

- protect Matrix recovery material and backup archives;
- do not publish generated secrets, tokens, passwords, recovery keys, or private diagnostics.

Automatic Kanban dispatch and skill writing are real agent capabilities. They are not a security sandbox.

================================================================================
16. UNINSTALL OR INTENTIONAL CLEAN-HOST RESET
================================================================================

NORMAL LATTICEVALE UNINSTALL
Use the shipped `installer\Uninstall-LatticeVale.ps1` and read every scope/preservation prompt. Normal uninstall is preservation-first: it does not unregister WSL and should be used when you merely want to remove LatticeVale or retain the distro/stack for recovery.

v14.4.5 intentionally aborts normal uninstall if stack metadata indicates Docker runtime may still exist but the Docker daemon cannot be inspected. Start/repair Docker in the selected distro and rerun the uninstaller; do not work around this by manually deleting Windows integration files first. If an ownership-modified task or shortcut is retained, the uninstaller also retains support files it still references rather than breaking that retained object.

INTENTIONAL FRESH WSL + LATTICEVALE BASELINE
Use tools\Reset-LatticeVale-CleanHost.ps1 only when you deliberately want an intentionally destructive clean-host rebuild. If `-RemoveWslRuntime` is selected, **ALL WSL distributions registered to the current Windows user are permanently unregistered**, not merely the distro used by LatticeVale. It is separate from `installer\Uninstall-LatticeVale.ps1` so ordinary uninstall/repair cannot accidentally cross this boundary.

1. Copy/extract the LatticeVale release containing the reset tool somewhere OUTSIDE any source folder you intend to delete.
2. Open PowerShell as Administrator.
3. Run a dry run first. Example:

   powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File .\tools\Reset-LatticeVale-CleanHost.ps1 -RemoveWslRuntime -RemoveLegacyHermesFoundry -DeleteLatticeValeSource -LatticeValeSourcePath "C:\path\to\old\LatticeVale"

4. Read every `WOULD:` line. `-RemoveWslRuntime` means ALL WSL distributions registered to the current Windows user will be permanently unregistered, not merely the LatticeVale distro. Stop if that is not what you intend. The dry run must reach its explicit completion message without a PowerShell error before you proceed to `-Execute`; the current release includes the heterogeneous Scheduled Task action compatibility fix introduced in v14.3.43.
5. When the dry-run inventory is correct, rerun the same command with `-Execute`.
6. Type the exact confirmation `CLEAN-RESET`.
7. Reboot Windows after the reset before reinstalling WSL.
8. Reinstall WSL and a supported Ubuntu WSL2 distro using Microsoft's current supported procedure, create the Linux user, verify the distro launches normally, then run LatticeVale as a fresh install.

The clean-host reset removes only Windows integrations it can attribute to LatticeVale or the explicitly selected legacy pre-LatticeVale Foundry cleanup. It deliberately does NOT disable/uninstall Hyper-V, HypervisorPlatform, VirtualMachinePlatform, HNS, Windows Tailscale, Obsidian, unrelated firewall/HNS objects, or a standalone `%USERPROFILE%\.hermes` directory. Global `.wslconfig*` files are removed only with `-RemoveWslRuntime` so the rebuilt WSL starts without inherited LatticeVale/Foundry host overrides.

17. VALIDATION LIMITS
================================================================================

The release includes source/static regression coverage and exact release-manifest verification, while WINDOWS-INTEGRATION-TEST-MATRIX.md documents the separate live Windows/WSL validation boundary. No installer can prove every third-party provider, Windows security product, Tailscale policy, GPU driver, network topology, or future upstream service behavior in advance. Treat live provider/network/account behavior as an integration boundary and use Verify/Resume rather than destructive resets when one of those external systems changes.

POLICY v11 MODEL-AWARE OLLAMA / HONCHO NOTE:
When managed Ollama is selected, LatticeVale fingerprints the installed text-model and embedding-model artifact sizes plus OLLAMA_CONTEXT_LENGTH. A CPU-backed clean install can begin with a 4096 MiB provisional floor before downloads exist, then performs a second bounded model-aware resource reconciliation after model download and before inference verification. GPU-backed installs also persist GPU topology/overhead and verify actual PROCESSOR offload with bounded `ollama ps` evidence before retaining GPU-sized assumptions. If the selected model and service minima cannot fit, the installer refuses the unsafe plan. Honcho receives an adaptive supported request timeout only while that timeout remains LatticeVale-owned; explicit user timeout values are preserved. `./manage.sh status` reports memory.max using a short delta sample so a historical lifetime count is not mislabeled as current pressure.
